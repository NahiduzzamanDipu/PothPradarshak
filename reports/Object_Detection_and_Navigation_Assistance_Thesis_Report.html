Abstract

Independent mobility remains a persistent difficulty for people with visual impairment, particularly on the footpaths of dense South Asian cities where the walking surface is frequently obstructed by parked vehicles, poles, street vendors and damaged pavement. The white cane detects obstacles only on contact and conveys nothing about what an obstacle is, while camera-based assistive systems reported in the literature are largely trained on Western urban imagery that does not represent this environment.

This thesis presents VisionAssist AI, a real-time assistive prototype that detects obstacles from a single monocular camera and converts them into spoken navigation guidance in Bengali and English. A dataset of 2,787 Dhaka footpath images was assembled from an initial pool of 21,359 unlabelled images, de-duplicated by perceptual hashing, and annotated for nine obstacle classes through a machine-assisted workflow in which an open-vocabulary detector proposed candidate boxes for human review. A YOLO11n detector was fine-tuned on the resulting 2,782 annotated images for 100 epochs on an NVIDIA RTX 3050 Ti.

Detections are converted into guidance by a deterministic pipeline rather than a second learned model: bounding-box geometry yields a horizontal zone (left, centre, right) and an apparent-proximity band, a priority function ranks obstacles, and an event-based announcement policy with a configurable cooldown decides when speech is warranted. Guidance sentences are constructed by a template grammar that handles Bengali subject–object–verb order and animacy-dependent numeral classifiers, and are spoken through a neural text-to-speech voice. The same pipeline serves three input modes: live camera, uploaded image, and uploaded recorded video.

On a held-out test split of 276 images the model achieves mAP@0.5 of 0.419 and mAP@0.5:0.95 of 0.297, with precision 0.645 and recall 0.404. Performance is strongly class-dependent: person (AP@0.5 = 0.837) and parked_vehicle (0.781) are detected reliably, whereas pothole and open_drain obtain zero recall. The cause is identified as annotation scarcity rather than model capacity — these classes had 17 and 12 training instances respectively, because the open-vocabulary annotation aid could not propose candidates for ground-surface defects. End-to-end throughput is 22.9 FPS in live camera mode and 13.7 FPS in video mode.

The contribution of this work is threefold: a reproducible machine-assisted annotation pipeline for an unlabelled Bangladeshi footpath corpus; an explainable, non-learned navigation layer whose behaviour can be audited line by line; and an empirical demonstration that open-vocabulary annotation transfers well to common object categories but fails on the ground-surface hazards that matter most for this application. The system is an assistive prototype and is not proposed as a sole navigation aid.

Keywords: Object Detection; YOLO11; Computer Vision; Navigation Assistance; Visually Impaired; Deep Learning; Bengali Speech Guidance; Assistive Technology.

Chapter 1Introduction

1.1 Background

Sight supplies most of the information a pedestrian uses to move safely: what lies ahead, how far away it is, and whether the surface can be trusted. When that channel is absent, the same information must be recovered some other way. The World Health Organization estimates that at least 2.2 billion people live with a near or distance vision impairment [1], and mobility is consistently among the functions most affected.

The white cane remains the dominant aid, and for good reason: it is inexpensive, needs no power, and gives immediate tactile feedback. Its limitation is equally clear. It reports contact, not category. A cane tells the user that something is there roughly one step before they reach it, but not whether that something is a parked motorcycle, a vendor's stall, or the edge of an open drain — distinctions that determine whether the correct response is to step around, stop, or retreat.

Computer vision offers a way to supply the missing semantic layer. Object detection — locating and classifying multiple objects in a single image — has become practical in real time since the introduction of single-stage detectors. Redmon et al. reframed detection as a single regression problem in YOLO [2], removing the separate region-proposal stage used by two-stage approaches such as Faster R-CNN [3]. Subsequent work in both families improved accuracy substantially [4], [5], [6], and the YOLO line in particular has been refined across many generations, with YOLO11 [7] the version used in this work.

For an assistive application, detection alone is insufficient. A list of bounding boxes must be turned into something a person can act on without seeing the screen, which requires deciding which detections matter, expressing their position in egocentric terms, and delivering the result as speech. Each of those steps introduces design questions that detection accuracy does not answer, and they occupy much of this thesis.

1.2 Problem Statement

The problem addressed here is the following: given a single monocular camera carried by a visually impaired pedestrian, how can obstacles on a Bangladeshi footpath be detected and communicated as timely, non-overwhelming spoken guidance in the user's own language?

Three sub-problems follow. First, no annotated detection dataset exists for this environment, and the classes that matter locally — rickshaws and other vehicles parked across the walkway, poles planted mid-footpath, uncovered drains — are not the classes for which public datasets provide labels. Second, the output must be selective: a detector running at over twenty frames per second produces far more detections than can be spoken, so the system must decide when silence is correct. Third, the guidance must be delivered in grammatical Bengali, which is not simply a matter of substituting words into an English sentence pattern.

1.3 Motivation

The immediate motivation is environmental. Footpaths in Dhaka are frequently interrupted: vehicles park across them, construction material is stored on them, poles and trees stand in the middle of them, and drain covers are missing often enough that falling into one is a realistic hazard rather than a hypothetical. A system trained on European or North American street imagery does not encounter these conditions, and will not have learned the object categories that describe them.

A second motivation is practical accessibility. Smartphone and laptop cameras are already widely available, and a system that runs on commodity hardware without a cloud connection avoids both the recurring cost and the latency of remote inference. This matters for an application where a delayed warning is equivalent to no warning.

A third motivation is methodological, and emerged during the work rather than preceding it. Annotating a detection dataset by hand is the step at which student projects of this kind commonly stall. Establishing whether an open-vocabulary detector can reduce that burden — and measuring honestly where it cannot — is useful independently of the assistive application.

1.4 Research Gap

Camera-based assistive navigation is an established research area, and several deployed and prototype systems are reviewed in Chapter 2. The gap addressed here is narrower than "no system exists", which would not be an accurate claim.

The gap is one of domain and class coverage. Systems reported in the literature typically either detect the generic object categories supplied by COCO [8] — which include person, car and chair but not pothole, open_drain or the footpath edge — or rely on proximity sensing that classifies nothing. Work specific to South Asian pedestrian infrastructure is comparatively sparse, and the ground-surface hazards characteristic of it are correspondingly under-represented in available training data.

A secondary gap concerns the guidance layer. Papers in this area often describe detection performance in detail while treating the conversion from detections to speech as an implementation detail. Since that conversion determines whether the system is usable at all, this thesis specifies and evaluates it explicitly.

1.5 Aim

To design, implement and evaluate a real-time assistive system that detects footpath obstacles from a monocular camera and delivers prioritised navigation guidance as Bengali or English speech, using a detection model trained on locally collected imagery.

1.6 Objectives

  1. To assemble and annotate a detection dataset of Bangladeshi footpath scenes covering obstacle classes relevant to pedestrian navigation.
  2. To evaluate whether an open-vocabulary detector can generate usable candidate annotations, and to quantify per class where it succeeds and where it fails.
  3. To train a single-stage detector on the annotated dataset and report precision, recall and mean average precision on a held-out test split.
  4. To implement a spatial analysis stage that assigns each detection a horizontal zone and an apparent-proximity band from bounding-box geometry.
  5. To design an announcement policy that prioritises hazardous obstacles and suppresses repetition, and to specify it in a form that can be inspected and justified.
  6. To generate grammatical guidance sentences in Bengali and English and deliver them as speech.
  7. To support three input modes — live camera, uploaded image and uploaded recorded video — through a single detection pipeline, and to measure runtime performance in each.

1.7 Research Questions

  1. RQ1. What detection performance can a nano-scale YOLO11 model achieve on a locally collected footpath dataset of approximately 2,800 annotated images, and how does performance vary across obstacle classes?
  2. RQ2. To what extent can an open-vocabulary detector substitute for manual annotation, and for which object categories does this substitution break down?
  3. RQ3. Can a deterministic, non-learned navigation layer convert detections into guidance that is both prioritised and sufficiently infrequent to be usable?
  4. RQ4. What runtime performance is achievable on a consumer laptop GPU across live camera, image and recorded video input?

1.8 Scope

Within scope. Monocular RGB input; nine outdoor footpath obstacle classes trained on project data; twelve indoor furniture classes supplied by a pre-trained model; horizontal position estimation; apparent-proximity estimation from bounding-box area; priority ranking and announcement suppression; Bengali and English sentence generation and speech; a browser-based interface with three input modes; evaluation on a held-out test split and measured runtime performance.

Outside scope. Metric distance estimation (no depth sensor or depth network is used, and the system never states a distance in metres); route planning or GPS navigation; object tracking across frames; obstacle detection at night or in rain, since the collected imagery is daytime; formal user trials with visually impaired participants, which would require ethical approval not sought for this work; and deployment to embedded or mobile hardware.

On the absence of user trials. This is a genuine limitation and is treated as such throughout. Section 5.12 explains why no navigation-accuracy percentage is reported: measuring whether guidance is correct requires ground-truth judgements from users who rely on it, and no such evaluation was conducted. Reporting a number in its place would be meaningless.

  2. An empirical characterisation of open-vocabulary annotation on this domain: 24,010 candidate boxes generated in 5.6 minutes, with per-class analysis showing reliable transfer for common objects and near-total failure for ground-surface defects (Section 5.2).
  3. A trained YOLO11n detector for nine Bangladeshi footpath obstacle classes, with per-class results reported including the classes that fail.
  4. An explainable navigation layer — priority scoring, event-based announcement and cooldown — specified in full and implemented without any learned component.
  5. A bilingual guidance generator that handles Bengali subject–object–verb order and animacy-dependent numeral classifiers rather than translating word by word.
  6. A single detection pipeline serving three input modes, with measured throughput for each.

Chapter 2Literature Review

2.1 Assistive Technology for Visually Impaired People

Assistive mobility devices are commonly divided into electronic travel aids, which detect obstacles; electronic orientation aids, which help establish position and route; and position locator devices. Surveys of the area [9] observe a recurring trade-off: devices that are simple and reliable convey little information, while devices that interpret the scene richly tend to be heavier, costlier, or dependent on infrastructure.

Early electronic aids used ultrasonic or infrared ranging to signal proximity through vibration or tone. These remain useful because they are cheap and work in darkness, but they are fundamentally category-blind: a wall and a pedestrian at the same range produce the same signal. The motivation for vision-based aids is precisely to add the category information that ranging sensors cannot supply.

2.2 Computer Vision-Based Navigation

Vision-based assistive navigation typically combines a camera, a scene-understanding component, and a non-visual output channel. Reported designs differ mainly in where computation occurs and what is communicated. Systems that offload inference to a server achieve higher accuracy but introduce network dependence and latency, both problematic when a warning must arrive before the user's next step. Systems that run on the device accept a smaller model in exchange for predictable timing — the trade-off this thesis makes, for the reasons given in Section 3.8.

A recurring design question is how much to say. Describing every detected object produces a narration that users cannot follow while walking, and several authors note that reducing output is as important as improving detection. This observation motivated the announcement policy in Section 3.11.

2.3 Object Detection

Object detection requires simultaneous localisation and classification. Before deep learning, detectors combined hand-designed features with sliding-window classifiers; the Viola–Jones framework [10] is the canonical example, effective for faces but not readily generalised. The shift to learned features followed the success of convolutional networks on large-scale classification [11].

Modern detectors are usually grouped into two families. Two-stage detectors first propose regions and then classify them; R-CNN and its successors, culminating in Faster R-CNN [3], established this approach and remain competitive in accuracy. One-stage detectors predict boxes and classes directly, trading some accuracy for a large gain in speed — SSD [4] and RetinaNet [5], the latter introducing focal loss to address foreground–background imbalance, are representative. More recently, transformer-based detectors such as DETR [12] have removed hand-designed components including non-maximum suppression, at the cost of longer training schedules.

2.4 YOLO-Based Object Detection

YOLO [2] treats detection as a single regression from image pixels to box coordinates and class probabilities, evaluated in one forward pass. This design is what makes real-time operation attainable, and successive versions have refined it while preserving that property: YOLO9000 [13] introduced anchor boxes and joint classification–detection training, YOLOv3 [14] added multi-scale prediction, and YOLOv4 [6] consolidated a range of training and architectural improvements. Recent iterations released as engineering frameworks rather than papers, including YOLOv8 and YOLO11 [7], provide model scaling from nano to extra-large, allowing the accuracy–latency operating point to be chosen for the target hardware. That scaling property is directly relevant here, and Section 3.8 explains why the nano variant was selected.

2.5 Deep Learning for Object Detection

Detection performance depends heavily on the quantity and relevance of labelled data. Public benchmarks — PASCAL VOC [15] and COCO [8] — provide both training data and standard evaluation protocol, and the mAP metric used in Chapter 5 follows the COCO convention of averaging over intersection-over-union thresholds from 0.5 to 0.95.

For domains not represented in these benchmarks, transfer learning from a pre-trained backbone is standard practice and is what this work does: training begins from COCO-pretrained weights and fine-tunes on the project dataset. Training from random initialisation on fewer than two thousand images would be expected to underfit badly.

Open-vocabulary detection is a more recent development directly relevant to the annotation problem. YOLO-World [16] combines a YOLO detector with vision–language embeddings derived from CLIP-style training [17], allowing detection of categories specified by text prompts without category-specific training data. This capability is used in Section 3.6 to generate candidate annotations, and its per-class reliability is measured in Section 5.2.

2.6 Navigation and Spatial Awareness

Converting detections into spatial guidance requires an egocentric frame. A common and computationally trivial approach is to partition the image horizontally and report which region an object occupies, which is the method adopted here (Section 3.10).

Estimating distance from a single camera is considerably harder. Bounding-box area is only a proxy, because apparent size confounds true distance with object size. Monocular depth estimation networks such as MiDaS [18] can recover relative depth from a single image, but add inference cost and were not integrated here; the interface is designed to accept such a component later (Section 7.4). This thesis therefore reports proximity bands rather than distances, and Section 3.10 states that limitation explicitly.

2.7 Voice-Based Assistance

Speech is the natural output channel when the visual one is unavailable, but it is serial and occupies the user's attention. Two consequences follow. First, message ordering matters: the most important obstacle must be spoken first, since the user may act before the sentence finishes. Second, message frequency must be controlled, because continuous narration both masks environmental sound and becomes fatiguing. These considerations shape the priority and cooldown mechanisms described in Section 3.11.

2.8 Bengali Speech Assistance

Bengali text-to-speech has improved substantially with neural synthesis, and several commercial services now provide Bengali voices of usable quality. Generating the text to be spoken, however, is a separate problem. Bengali is a subject–object–verb language, so a sentence generated by substituting Bengali words into an English template produces incorrect word order. Bengali also uses numeral classifiers whose form depends on animacy — একজন for people, একটি for inanimate objects — so a generator that ignores animacy produces grammatically wrong output. Both properties are handled explicitly in Section 3.12.

2.9 Existing Related Systems

Reported camera-based assistive systems for visually impaired users generally follow one of three patterns. The first uses a pre-trained detector on generic categories and announces what it sees; this is straightforward to build and requires no dataset work, but inherits the category vocabulary of the pre-training corpus. The second couples a detector with a depth sensor to give distance as well as identity, which improves guidance quality at the cost of specialised hardware. The third performs scene description on a server, which permits larger models but introduces latency and connectivity dependence.

This work follows the first pattern architecturally, but replaces the generic category vocabulary with classes annotated specifically for the target environment. That substitution is the main point of difference, and the results in Chapter 5 show both its benefit for locally relevant categories and its cost when annotation coverage is thin.

Chapter 3Methodology

3.1 System Overview

The system converts a stream of camera frames into occasional spoken sentences. Between those two points sit five stages: detection, spatial analysis, priority ranking, announcement decision, and sentence generation. Only the first is a learned model. The remaining four are deterministic, and Section 3.11 explains why that separation was chosen rather than adopted by default.

The design constraint that shaped everything else is that the output channel is serial and slow. A detector producing twenty-three frames per second generates on the order of 1,400 detections per minute; speech can convey perhaps ten short sentences in the same time. The system is therefore better understood as a filter than as a describer, and most of the engineering effort went into deciding what not to say.

3.3 Input Sources

Three input modes are supported, and they share one detection path. This is an architectural decision rather than a convenience: an uploaded video becomes the pipeline's frame source, exactly as a webcam does, so video is processed frame by frame as it streams rather than analysed in full and replayed afterwards.

  • Live camera. A device index or a network stream URL, opened through OpenCV. The capture layer runs in its own thread and always holds the newest frame.
  • Uploaded image. A single frame decoded and passed through the same detector, spatial analyser and navigation engine, producing one annotated image and one instruction.
  • Uploaded recorded video. Assigned as the capture source, played at its native frame rate, with pause, resume and restart control.

Because the three modes share components, a change to the detector or the navigation rules takes effect in all of them, and behaviour cannot silently diverge between what is demonstrated on a recording and what happens on a live camera.

The starting point was a pool of 21,359 images collected from several sources and containing no annotations of any kind. Inspection showed the pool to be heterogeneous: a large group of small traffic-sign crops, a group of Indonesian sidewalk photographs, a group of Dhaka footpath scenes, dashcam frames recorded by the author, and assorted unrelated images.

Only the Dhaka footpath group is in the target domain, and the dataset used for training was restricted to it. The selection criterion was recorded so the result is reproducible: purely numeric .jpg filenames at exactly 256×256 pixels, which isolates that group from the others.

3.5 Data Collection

The footpath images were collected in Dhaka at pedestrian height, framing the walking surface and the space immediately ahead. A separate group of road-level frames was recorded by the author from a moving vehicle; these were retained in the pool but excluded from the training set, because a dashcam viewpoint does not match what a pedestrian's camera sees, and mixing the two would teach the model an inconsistent relationship between image position and walking-path relevance.

No images of identifiable individuals were collected deliberately as subjects; people appear incidentally in public street scenes. The dataset was not published, and Section 6.9 discusses the ethical considerations that apply.

Candidate boxes were generated by YOLO-World [16], an open-vocabulary detector that accepts natural-language prompts. Each thesis class was described by several prompts rather than a bare class name, since descriptive phrases produce markedly better recall from this model — for example pothole was queried as "pothole", "broken pavement", "hole in the road surface" and "damaged footpath tiles". Thirty-five prompts were mapped back to the nine classes.

Two mechanical failure modes were filtered automatically before any human saw the output. The first is whole-image boxes, where the model matches the scene rather than an object; boxes covering more than 55% of the frame were discarded. The second is duplicate boxes arising because several prompts map to one class and non-maximum suppression runs per prompt, not per class; class-wise suppression at 0.65 IoU was applied after the prompt-to-class mapping.

A custom review tool was written for the verification stage. It presents each image with its candidate boxes and supports accepting, deleting, reclassifying or drawing boxes from the keyboard. Images were ordered hardest-first, so that candidates for the hazard classes were reviewed before the easy ones.

An honest account of what the verification achieved. All 2,782 images were reviewed and accepted, but a comparison of the final label files against the machine output shows that the box count was unchanged for every image: no boxes were added, deleted or reclassified. The verification pass therefore confirmed the machine's proposals rather than correcting them.

This matters for interpreting Chapter 5. Where YOLO-World proposed nothing — which is the case for almost all ground-surface hazards — there was nothing for the reviewer to accept, and those classes consequently remained almost unannotated. The resulting label set is best described as machine-generated with human confirmation, and the zero-recall results in Section 5.5 follow directly from it.

3.7 Data Preprocessing

Preprocessing is deliberately light, since the images are already small and uniform.

  • Resizing. Images are letterboxed to 640×640 by the training framework, preserving aspect ratio.
  • Normalization. Pixel values are scaled to [0, 1]; no dataset-specific mean subtraction is applied.
  • Label format. YOLO format — one text file per image, one line per object, class_id cx cy w h with coordinates normalised to [0, 1]. Images with no objects keep an empty label file, which YOLO treats as a valid background example.
  • Augmentation. Mosaic (disabled for the final 10 epochs), horizontal flip with probability 0.5, rotation of ±5°, and HSV value jitter of 0.4.

The augmentation choices reflect the domain. Rotation is small because a hand-held or chest-mounted camera is rarely perfectly level but a footpath scene is never inverted; vertical flipping is not used for the same reason. Brightness jitter is comparatively strong because Dhaka footpaths alternate between direct sun and deep shade within a single frame.

3.10 Object Position Estimation

Each detection is assigned a horizontal zone from the centre of its bounding box.

        (বামে)             (সামনে)             (ডানে)

Figure 3.4 — Horizontal zone partitioning. Both boundaries are runtime-configurable.

An apparent-proximity band is derived from the fraction of the frame the box occupies:

area_ratio = (wbox × hbox) / (Wframe × Hframe) (3.3)

with area_ratio ≥ 0.15 classified NEAR, ≥ 0.04 MEDIUM, and otherwise FAR. All four thresholds are configurable and are re-read on every frame, so adjusting them in the interface takes effect immediately.

This is proximity, not distance, and the distinction is not cosmetic. Apparent size confounds distance with object size: a bus thirty metres away can occupy more pixels than a chair two metres away. The estimate is therefore comparable between objects of similar real-world size and meaningless across classes.

The interface accordingly never displays a distance in metres. An earlier interface mock-up produced during design showed values such as "2.4 meters"; these were removed, because printing a fabricated distance in a device intended for navigation is worse than printing nothing. The spatial module defines a DepthProvider interface so that a monocular depth network such as MiDaS [18] or a stereo sensor can replace the area heuristic without changes elsewhere.

3.11 Navigation Decision System

The navigation layer contains no learned component. A model that maps detections to instructions was considered and rejected: supervising it would require thousands of scene–instruction pairs judged by blind users, which do not exist; its failures would be difficult to enumerate in advance, which is unsatisfactory in assistive software; and its decisions could not be justified individually during examination. The rules involved are also short enough to state completely, which is what the remainder of this section does.

Priority. Every detection receives a score:

ComponentContributionRationale
Danger class (pothole, open_drain, stairs, curb, pole, vehicle)+100Fall or collision hazard
Indoor obstacle (chair, table, bed, …)+40Collision, but not a fall
Position is CENTER+50Directly in the walking path
Proximity NEAR / MEDIUM / FAR+30 / +12 / 0Urgency rises as the object nears
Detector confidence+10 × confBreaks ties without outweighing geometry

Table 3.6 — Priority score components.

The weights are chosen so that class and position dominate: a pothole ahead always outranks a chair to the left, and no confidence value can reverse that ordering. This is deliberate, since confidence reflects the detector's certainty, not the consequence of being wrong.

When to speak. Speech is triggered by change, not presence. An object already announced and unchanged is not news, so the engine announces only when one of the following holds: a previously unseen object appears; proximity worsens (FAR → MEDIUM → NEAR); or an object moves into the CENTER zone. Two timers then apply: a per-object cooldown of 3.0 s and a global minimum gap of 1.2 s between any two utterances. A genuine escalation to NEAR overrides the per-object cooldown.

A detail that took two attempts to get right. The engine compares an object's current state against its state at the last announcement, not at the previous frame. An earlier implementation compared against the previous frame, with the consequence that an escalation occurring while the cooldown was active was consumed and never spoken. The escalation most likely to be suppressed that way is MEDIUM → NEAR — precisely the transition the user most needs to hear.

3.12 Voice Guidance

Sentences are constructed by a template grammar rather than translated, so that Bengali output is generated natively rather than derived from English word order.

Two properties of Bengali are handled explicitly. Word order is subject–object–verb, so clauses are assembled tail-last with the verb আছে closing the sentence. Numeral classifiers depend on animacy: একজন is used for people and একটি for inanimate objects, and using the latter for a person is grammatically incorrect. Animacy is therefore tracked per class rather than assumed.

When several objects are reported, they are combined into a single sentence with one closing verb rather than read as separate sentences. For a listener who cannot see the scene, one flowing sentence is faster to absorb than three restarts of "There is …", and repeating আছে after every clause is one of the clearest markers of machine-generated Bengali.

4.3 Model Loading

Weights are located by searching a fixed ordered list of paths, so no absolute path is embedded in the code and a trained model is picked up automatically after training completes. If no trained model is found the system loads the COCO-pretrained network as a placeholder and announces that fact in three places — the log, the video overlay, and a banner across the interface — so that a placeholder run cannot be mistaken for a thesis result. Both models are loaded once at startup and reused; a warm-up inference is performed so that the first reported frame rate is honest.

4.4 Camera Module

Capture runs in a dedicated thread that keeps only the newest frame. This matters because VideoCapture.read() blocks: if the inference loop called it directly, a slow model would accumulate a backlog of stale frames and the displayed view would drift seconds behind reality. Dropping frames is the correct behaviour for a navigation aid, where a fresh frame is worth more than a complete sequence.

Two failure modes encountered during development are handled explicitly. First, a camera that opens successfully may still deliver nothing usable: virtual cameras stream solid black or a placeholder graphic when no source is attached. The capture layer therefore samples several frames after opening and tests whether they carry any image content, preferring a backend that returns a real image and warning in the interface when none does. Second, a device may return black on one platform backend while working on another, so DirectShow, Media Foundation and the OpenCV default are each attempted in turn.

4.5 Image Upload Module

An uploaded image is decoded and passed through the pipeline's own detector, spatial analyser and navigation engine, so it is judged by exactly the same model and thresholds as the live camera. The module does not touch the capture layer, which means an image can be analysed while a live session continues. The response contains the annotated image, the per-object table and the generated instruction.

4.6 Recorded Video Module

An uploaded clip is written to disk and assigned as the capture source. Because the capture layer already supports file sources, no separate video-processing implementation exists: playback control (pause, resume, restart, progress reporting) was added to the capture layer, and everything downstream is unchanged. Uploads are limited to 200 MB and older clips are pruned so a demonstration session does not fill the disk.

4.7 Object Detection Module

This is the only module that imports Ultralytics, which confines the framework dependency to one file. It converts raw model output into the dictionary structure used throughout the rest of the system, performs the dual-model fusion described in Section 3.8, and draws the overlay. Boxes are drawn in red with a short label of class name and confidence; position and proximity are shown in the side panel rather than on the box, because repeating them on the frame produced labels wide enough to overlap in crowded scenes.

4.8 Navigation Module

The navigation engine holds a small amount of state: for each tracked key — a (class, position) pair rather than a box identity — it records when the object was last seen and what its proximity and position were at the last announcement. Using (class, position) as the key is a deliberate simplification: without a tracker the system cannot know whether this is the same person as the previous frame, and for guidance purposes "a person on your left" is the same information either way.

4.9 Voice Module

Sentence generation and speech synthesis are separated. The generator is pure text transformation and is unit-testable without audio. The synthesiser runs a daemon worker thread consuming a bounded queue; when the queue is full the oldest pending phrase is dropped, since a stale warning is worse than a missed one. Backend selection is decided at runtime from a capability probe rather than assumed, and a synthesis failure never propagates into the detection loop.

4.10 User Interface

The interface is a single browser page served by the backend. The processed video arrives as an MJPEG stream, and all other state is polled as JSON four times per second. Bounding boxes are drawn into the video frames by OpenCV rather than overlaid in the browser, which guarantees that a box can never drift out of alignment with the frame it was computed from.

An input-mode selector switches between live camera, image and video, showing only the controls relevant to the active mode. Every displayed value — frame rate, inference time, object count, average confidence, model name — comes from the backend; none is simulated.

4.12 Performance Optimization

  • Single model load. Both networks are loaded once at startup and reused.
  • Three threads. Capture, inference and speech run independently, so voice never blocks inference and inference never blocks the HTTP layer.
  • Newest-frame-wins capture. Stale frames are discarded rather than queued.
  • Optional frame skipping. Inference can run on one frame in n while the overlay reuses the previous boxes, trading detection latency for display smoothness.
  • Mixed-precision training to fit the 4 GB memory budget.
  • Adjustable JPEG quality for the stream, trading bandwidth against latency.
  • Explicit resource release. Capture handles are released on stop; the audio cache is pruned periodically.

5.1 Experimental Setup

All experiments were run on the configuration in Table 4.1. Detection metrics were computed on the test split of 276 images, which was held out from training and from the validation set used for early stopping, and which was formed at the near-duplicate cluster level so that no test image has a near-copy in training. Evaluation used a confidence threshold of 0.001 and NMS IoU of 0.60, following the standard convention for mAP computation.

Runtime measurements were taken from the running application through its own state endpoint, so they reflect end-to-end throughput including capture, inference, overlay drawing and JPEG encoding — not model forward-pass time alone, which is reported separately.

5.6 Detection Examples

5.7 Live Camera Testing

With the trained model and the indoor model both active on the GPU, live camera operation was measured at 22.9 FPS end-to-end with a reported inference time of 42.8 ms at a capture resolution of 1280×720. Detection, zone assignment, guidance generation and speech all functioned in this mode.

Two observations from live testing are worth recording because they affected the design. First, the confidence threshold matters more than expected: at the default 0.50 the model detected very little in practice, and a threshold near 0.30 was needed for useful behaviour — consistent with the modest overall recall in Table 5.3. Second, pointing the camera at an indoor scene produced no detections from the thesis model, which is the correct outcome for a model trained exclusively on footpaths and was the reason the secondary indoor model was added.

5.8 Image Testing

Single-image analysis was measured over three consecutive runs on the same 640×407 image, giving inference times of 82.2 ms, 105.8 ms and 55.5 ms — the variation reflecting GPU scheduling rather than image content. Five objects were detected consistently across all runs, with identical classes and positions, confirming that the image path is deterministic.

The generated guidance for that image was "আপনার বাম পাশে খুব কাছে একটি বিছানা আছে।" in Bengali and "There is a bed close on your left." in English, correctly selecting the single NEAR object over three FAR ones.

5.9 Recorded Video Testing

A 90-second clip at 6 FPS (540 frames) assembled from dataset imagery was processed in streaming mode. Measured throughput was 13.7 FPS with an inference time of 57.4 ms, lower than live mode because both models run while the file is simultaneously decoded.

Playback control was verified explicitly: with playback paused, the reported position remained at 0:13 across a subsequent interval and did not advance; resuming advanced it to 0:17; restart returned it to 0:02. Requesting playback control while a live camera was active returned an explanatory error rather than silently failing.

Over the clip, 39 distinct instructions were generated from 329 detections across 90 analysed frames. That ratio is the announcement-suppression mechanism working as intended: without it the same stationary obstacle would have produced an utterance on every frame in which it appeared.

5.12 Navigation Accuracy

No navigation-accuracy figure is reported, and none should be inferred.

Evaluating whether guidance is correct requires ground truth about what a user should have been told in each situation. Constructing that ground truth means having visually impaired participants use the system and judge whether each instruction was appropriate, timely and sufficient — a study requiring ethical approval and participant recruitment that were outside the scope of this work.

What can be stated is narrower and verifiable: the zone assignment follows deterministically from Equations (3.1)–(3.2) and was confirmed correct on inspected examples; the priority ordering follows Table 3.6 and was observed to select the NEAR centre object over FAR peripheral ones; and announcement suppression reduced 329 detections to 39 utterances on the test clip. The usefulness of that behaviour to a blind pedestrian remains unmeasured.

Error characteristics observed. The confusion matrix indicates that missed detections dominate over class confusion, consistent with recall (0.404) being substantially lower than precision (0.645). 5.14 Result Discussion

The headline figure — mAP@0.5 of 0.419 — understates performance on the classes the model actually learned and overstates it on those it did not, because mAP averages uniformly over classes regardless of how many instances support each one. Read per class, the picture is clearer: two classes with thousands of examples reach AP@0.5 of 0.837 and 0.781, four classes with tens to hundreds of examples reach 0.24–0.36, and three classes with fewer than twenty examples are either unmeasurable or fail entirely.

The relationship between instance count and per-class AP is close to monotonic across the nine classes, which supports the interpretation that annotation coverage, rather than model capacity or training length, is the binding constraint. This is a useful negative result: it indicates that the productive next step is annotation of the hazard classes rather than a larger model or a longer schedule.

Set against the objectives in Section 1.6, objectives 1, 3, 4, 5, 6 and 7 were met, and objective 2 was met in the sense that open-vocabulary annotation was evaluated — with the answer being partly negative. The system as built detects people and vehicles reliably and communicates them appropriately, but does not yet detect the fall hazards that motivated the class list.

Chapter 6Discussion

6.1 Major Findings

Three findings emerge from the work, and they are of unequal importance.

The first is that a nano-scale detector fine-tuned on roughly nineteen hundred locally collected images is sufficient for the common obstacles on a Dhaka footpath. AP@0.5 of 0.837 for person and 0.781 for parked_vehicle is adequate for the guidance task, which does not require precise box regression — only a reliable class and an approximately correct horizontal position.

The second, and the more consequential, is that the annotation method determined the outcome more than any modelling decision. Open-vocabulary annotation was fast and effective for categories resembling its pre-training data, and produced essentially nothing for ground-surface hazards. Because the human review confirmed the machine's proposals rather than supplementing them, that gap propagated unchanged into the training set and then into the results.

The third is that the guidance layer did not need to be learned. Priority ordering, event detection and cooldown were sufficient to convert a dense detection stream into occasional sentences, and being deterministic they can be inspected, justified and adjusted without retraining.

6.2 Effectiveness of Object Detection

Detection effectiveness splits cleanly along instance count. Where the dataset provided thousands of examples the model performs well; where it provided tens it performs poorly; where it provided fewer than twenty it does not perform at all. The near-monotonic relationship between per-class instance count and AP (Table 5.4) is the clearest single result in this thesis.

Precision exceeding recall by a wide margin (0.645 against 0.404) indicates a conservative detector. For an assistive device the direction is preferable to the alternative: spurious warnings would erode trust quickly, and a user who is told about an obstacle can generally verify it with a cane. It does not, however, make missed detections acceptable, and the missed detections are concentrated in exactly the classes where a miss is most costly.

6.3 Navigation Assistance Performance

The navigation layer behaved as specified. The priority function consistently selected a near, centred object over peripheral or distant ones, and the ordering was traceable to Table 3.6 in every case examined. Combining several objects into one sentence rather than several worked well in testing and reduced the time to convey a scene.

The layer's quality is bounded by its input. Priority ranking cannot elevate an obstacle the detector never reported, so the hazard-class failures in Chapter 5 propagate directly into guidance: the system will not warn about a pothole, regardless of how correctly the priority rules are specified. This is worth stating plainly, because the navigation logic being correct might otherwise be mistaken for the system being safe.

6.4 Voice Guidance

Bengali generation handled the two grammatical features it was designed for — verb-final word order and animacy-dependent classifiers — correctly in all tested cases. Combining clauses under a single closing আছে produces noticeably more natural output than repeating the verb, which was the behaviour of the first implementation.

The dependence on a network service for Bengali speech is the main practical weakness. English synthesis is offline and instantaneous, but Bengali — the default and more important language for the intended users — requires connectivity. Installing a Bengali system speech voice would remove this dependence without any code change, since backend selection is made from a runtime capability probe.

6.5 Real-Time Performance

At 22.9 FPS end-to-end in live mode the system is comfortably real-time for walking pace, and the 19.0 ms model forward pass indicates substantial remaining headroom. Running two detectors concurrently within a 4 GB memory budget was feasible because both are nano-scale.

The relevant latency for an assistive device is not frame rate but the interval between a hazard entering view and the user hearing about it. That interval includes speech synthesis and playback, which for the network-based Bengali voice adds a delay not captured in the frame-rate figures. It was not measured, and Section 7.4 identifies it as necessary future work.

6.6 Recorded Video Performance

Video mode reached 13.7 FPS, lower than live mode because file decoding competes with inference. Since the design goal was streaming processing rather than maximum throughput — frames are processed and displayed as they are read, not analysed in advance — this is acceptable.

Reusing the capture layer for video rather than writing a separate video path proved valuable beyond saving effort: detection, navigation, voice and statistics behave identically across modes, so a demonstration on a recording is a faithful representation of live behaviour rather than a separate code path that might diverge.

6.7 Strengths

  • Detection classes chosen for the target environment rather than inherited from a general benchmark, so the vocabulary includes obstacles that matter locally.
  • A reproducible dataset pipeline with recorded selection criteria, de-duplication before annotation, and split-level leakage prevention.
  • An explainable guidance layer that can be audited and adjusted without retraining.
  • Bengali generated natively rather than translated, with grammatical features handled explicitly.
  • Real-time operation on commodity hardware with no cloud inference.
  • One detection pipeline serving three input modes, preventing behavioural divergence.
  • Honest reporting of failure: the interface never displays a fabricated distance, and the system announces loudly when it is running a placeholder model.

6.9 Ethical and Safety Considerations

This system is a research prototype. It has not been validated with visually impaired users, has known and substantial detection failures, and must not be treated as a sole navigation aid. Any deployment would need to position it as supplementary to a cane or guide dog, never as a replacement.

The most serious ethical risk is not that the system fails, but that it fails selectively in a way a user cannot perceive. A user who hears reliable warnings about people and vehicles may reasonably infer that silence means a clear path, when in fact the system is structurally incapable of reporting an open drain. That asymmetry between apparent and actual competence is more dangerous than uniformly poor performance would be, and it is the reason the zero-recall results are stated so prominently in this thesis rather than being averaged into an overall figure.

Two further considerations apply. The dataset consists of public street scenes in which people appear incidentally; no individual was recruited or photographed as a subject, and the dataset has not been published. Bengali speech synthesis transmits the generated sentence to a third-party service, which is a privacy consideration if the system were deployed — the sentences describe the user's immediate surroundings. An offline voice would remove this exposure.

Chapter 7Conclusion and Future Work

7.1 Conclusion

This thesis set out to build an assistive system that detects footpath obstacles from a monocular camera and communicates them as spoken guidance in Bengali and English, using a detector trained on locally collected imagery rather than a general-purpose benchmark.

The system was built and works. A dataset of 2,782 annotated Dhaka footpath images was assembled from an unlabelled pool of 21,359 through a documented selection, de-duplication and machine-assisted annotation pipeline. A YOLO11n detector fine-tuned on it achieves mAP@0.5 of 0.419 and mAP@0.5:0.95 of 0.297 on a held-out test split, with AP@0.5 of 0.837 for person and 0.781 for parked_vehicle. Detections are converted into guidance by a deterministic layer — zone assignment, priority scoring, event-based announcement and cooldown — and rendered as grammatical Bengali or English speech. The same pipeline serves live camera, uploaded image and recorded video input at 22.9 and 13.7 FPS respectively.

The system does not, however, do the thing that most motivated it. pothole and open_drain obtain zero recall, because the annotation method that made the dataset feasible could not propose candidates for ground-surface defects, leaving 17 and 12 training instances respectively. The result is a working assistive prototype that is reliable on people and vehicles and blind to the fall hazards it was designed to warn about. Establishing that limitation clearly, and tracing it to a specific and correctable cause, is a legitimate outcome of the work — but it is a limitation, not a success.

7.2 Research Contributions

  1. A documented, reproducible pipeline converting an unlabelled mixed-source pool into an annotated, de-duplicated footpath detection dataset, with leakage prevented at the split level.
  2. An empirical characterisation of open-vocabulary annotation on Bangladeshi footpath imagery, with per-class evidence of where it transfers and where it fails — a result that is useful to anyone attempting a similar dataset.
  3. A trained nine-class detector for this domain, with per-class results reported including the classes that fail.
  4. A fully specified, non-learned navigation layer whose behaviour can be audited line by line, including an event-comparison detail (compare against last announcement, not last frame) that a naive implementation gets wrong.
  5. A bilingual guidance generator handling Bengali verb-final order and animacy-dependent classifiers.
  6. A single detection pipeline serving three input modes with measured performance for each.

7.3 Limitations

The limitations are set out in Table 6.1. The three that most constrain the current system are the absence of hazard-class detection, the absence of metric distance estimation, and the absence of any evaluation with visually impaired users. The first is a data problem with a clear remedy; the second requires an additional sensing or modelling component; the third requires a study design and ethical approval rather than engineering.

7.4 Future Work

Immediate, and necessary before any claim of hazard detection.

  • Manually annotate 100–200 instances each of pothole, open_drain, stairs and curb. The unused image pool already contains a large number of pothole and stairs photographs, so the images exist; only the boxes are missing.
  • Retrain and re-evaluate, reporting per-class AP for the hazard classes specifically.
  • Apply class-balanced sampling or loss weighting so that rare classes contribute proportionally more gradient signal.

System capability.

  • Integrate monocular depth estimation [18] through the existing DepthProvider interface, replacing apparent-size proximity with relative depth and allowing the system to speak in distance terms without fabricating them.
  • Add object tracking so that guidance can refer to a specific object across frames and describe motion (approaching, receding) rather than only presence.
  • Measure hazard-to-speech latency end to end, which is the metric that actually matters for the user and which frame rate does not capture.

Data and deployment.

  • Extend collection to night, rain and artificial lighting, and to higher source resolution.
  • Export to ONNX or NCNN for smartphone deployment, which is the realistic form factor for a pedestrian aid; the current laptop implementation is a development platform, not a product.
  • Install or train an offline Bengali speech voice to remove the network dependence.

Evaluation.

  • Conduct a user study with visually impaired participants under appropriate ethical approval, measuring whether instructions are judged timely, correct and sufficient. Without this, the navigation layer's usefulness remains asserted rather than demonstrated.

Implemented in this work: nine-class footpath detection; twelve indoor classes via a pre-trained model; zone and proximity estimation; priority ranking; event-based announcement with cooldown; Bengali and English generation and speech; live camera, image and recorded video modes; browser interface.

Not implemented, and listed above as future work: hazard-class detection; depth estimation; object tracking; GPS or IMU integration; mobile deployment; offline Bengali speech; user evaluation.

def get_position(self, center_x, frame_width):
    frac = center_x / float(frame_width)
    s = self.settings
    if frac < s.get("zone_left_edge"):
        return LEFT
    if frac > s.get("zone_right_edge"):
        return RIGHT
    return CENTER

def get_proximity(self, bbox, frame_width, frame_height):
    x1, y1, x2, y2 = bbox
    area_ratio = ((x2 - x1) * (y2 - y1)) / float(frame_width * frame_height)
    if self.depth_provider is not None:        # extension point for real depth
        metres = self.depth_provider.depth_at(...)
        if metres is not None:
            return (NEAR if metres <= 1.5 else
                    MEDIUM if metres <= 4.0 else FAR), area_ratio
    s = self.settings
    if area_ratio >= s.get("near_area_ratio"):
        return NEAR, area_ratio
    if area_ratio >= s.get("medium_area_ratio"):
        return MEDIUM, area_ratio
    return FAR, area_ratio

I.2 — Priority scoring (backend/navigation/navigation_engine.py):

def priority_score(self, det):
    score = 0.0
    if det["class_name"] in DANGER_CLASSES:
        score += 100.0
    elif det["class_name"] in INDOOR_OBSTACLES:
        score += 40.0
    if det.get("position") == "CENTER":
        score += 50.0
    score += {"NEAR": 30.0, "MEDIUM": 12.0, "FAR": 0.0}.get(
        det.get("proximity", "FAR"), 0.0)
    score += float(det.get("confidence", 0.0)) * 10.0
    return score

def _generate_bn(object_name, position, proximity, urgent, overrides):
    name    = bengali_name(object_name, overrides)
    article = _bn_article(object_name, name)     # একজন for people, একটি otherwise
    place   = _BN_POSITION.get(position, "সামনে")
    prox    = _BN_PROXIMITY.get(proximity, "")

    # Subject-Object-Verb: [place] [proximity] [article] [noun] আছে।
    pieces = [place]
    if prox:
        pieces.append(prox)
    pieces.append(article)
    pieces.append(name)
    sentence = " ".join(pieces) + " আছে।"
    return "{} {}".format(_BN_WARN, sentence) if urgent else sentence

@staticmethod
def _merge(primary, secondary, iou_thr=0.55):
    """Keep only secondary boxes that do not overlap a thesis-model box.
       The thesis model always wins, because it is trained on this data."""
    return [d for d in secondary
            if not any(iou(d, p) > iou_thr for p in primary)]
